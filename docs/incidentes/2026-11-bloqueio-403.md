# Pós-mortem: bloqueio HTTP 403 da Caixa (novembro de 2026)

- **Status:** encerrado com coleta congelada
- **Dados exibidos no site:** lista de 15/11/2026
- **Redigido em:** 18/11/2026

## Resumo

A partir de 16/11/2026, a Caixa passou a responder HTTP 403 ao download do CSV de todas as 27 UFs quando a requisição partia do GitHub Actions. Do meu IP residencial, o mesmo arquivo continuou baixando normalmente. A coleta diária parou, o site ficou com os dados de 15/11/2026 e decidi não contornar o bloqueio.

A causa exata não é pública. A explicação mais provável é a combinação de dois fatores: a Caixa filtrar tráfego vindo de servidores em nuvem e o aumento de requisições que eu mesmo introduzi em 05/11, quando o snapshot passou a consultar as páginas de detalhe dos imóveis.

## Impacto

- O site deixou de receber atualizações: preços, quedas, imóveis novos e saídas da lista ficaram parados em 15/11/2026.
- Imóveis vendidos ou retirados depois dessa data continuam aparecendo até que a coleta volte. O aviso na home e em /status e o link para a página oficial de cada imóvel reduzem o risco de alguém agir com base em dado velho.
- Nenhum dado foi perdido. O banco e o snapshot versionado continuam íntegros.
- Três issues automáticas foram abertas e depois fechadas.

## Causa provável

1. **Filtro por origem.** O 403 acontece para qualquer UF a partir do GitHub Actions e não acontece de um IP residencial. Isso aponta para uma regra que trata faixas de IP de nuvem de forma diferente, e não para um problema no arquivo ou na URL.
2. **Aumento de volume causado pelo projeto.** Até 05/11, o projeto fazia 27 requisições por dia. Com a leitura das páginas de detalhe, passou a fazer cerca de 147, sempre do mesmo tipo de origem e no mesmo horário. O bloqueio começou 11 dias depois. Não tenho como provar a relação, mas é honesto registrar que essa mudança provavelmente contribuiu: ela aumentou a pegada do robô justamente sobre páginas que a lista em CSV já não exigia.

A Caixa não publicou aviso sobre a mudança, e não houve contato direto. Por isso as duas hipóteses ficam como prováveis, não confirmadas.

## Decisão

Não contornar o bloqueio. Isso exclui proxy, troca ou rotação de IP, execução a partir da minha rede residencial de forma automatizada e qualquer disfarce de navegador. Se a fonte decidiu barrar coleta automatizada vinda de nuvem, insistir por outro caminho seria desrespeitar essa decisão, e um projeto de portfólio não deve depender disso.

A coleta só volta se a Caixa liberar o acesso de servidores em nuvem ou oferecer um canal oficial para os dados.

## Lições

1. **Cada nova requisição à fonte é uma mudança de comportamento do robô.** A leitura das páginas de detalhe foi tratada como melhoria de interface, mas na prática multiplicou o volume de acesso. Mudanças desse tipo merecem a mesma revisão que uma mudança na coleta.
2. **O mínimo necessário é a melhor política.** A lista em CSV já é publicada para download. Uma requisição por UF por dia era um uso razoável; o cronômetro não justificava o custo para a fonte.
3. **Tratar 403 de forma diferente de 5xx.** Um 502 é falha temporária e faz sentido tentar de novo no dia seguinte. Um 403 em todas as UFs é sinal de recusa e deveria interromper as tentativas e avisar, em vez de abrir uma issue nova por dia.
4. **Avisar o usuário é parte do produto.** Quando os dados param, o site precisa dizer isso de forma visível, com a data, e não continuar prometendo atualização diária.
